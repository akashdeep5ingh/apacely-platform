# Worker ingress contract — local executable boundary

## Authority and scope

Separately authorized local durable replay implementation atop clean baseline `98d884c90a6f7422c9c780492ffa0fb6fe953508`, preserving the earlier authority hardening. Historical documentation-only exclusions remain applicable outside this local slice. `src/worker-ingress.ts` exports a reusable class with `handle(Request)`; it is **not a Worker entrypoint**, has no default export or production `fetch`, deployment configuration, public endpoint or real verifier. Earlier tests construct Requests inside an in-memory test-only Worker service-binding RPC harness; the local HTTP integration below adds actual fetch-event dispatch without enabling production ingress. Real existing shared `Processor`/D1 acceptance commits state and pending outbox atomically. No policy duplication, consumer, provider, UI, resource mutation, deploy, commit or push is included.

All route, size, timestamp-window and response choices below are **synthetic local test policy**, not approved production security policy. Qualification remains `mock-qualification-v1`, not client eligibility or consent policy.

## Trust boundary and lifecycle

1. Generate an internal UUID request ID (ignore external correlation headers).
2. Require POST, exact `/v1/ingress/{provider}` with provider `[a-z][a-z0-9_-]{0,31}` and no query. Version 1 is the only route version.
3. Require `application/json` (optional UTF-8 charset); reject Content-Encoding. Read the stream with a 16,384-byte limit, cancel on overflow, never trust Content-Length as the actual size. Broken streams reject safely. Fatal UTF-8 decode precedes JSON parsing.
4. Reject duplicate decoded JSON property names, including escaped-equivalent names, before JSON.parse can silently choose the last value. Inspect all object nesting; depth greater than four fails. The lexical inspection is not a replacement JSON parser: JSON.parse still rejects malformed syntax. Unknown fields (including tenant_id/environment/source_binding) fail at top level and qualification level.
5. Reuse `validateInput` for required exact fields, types, safe positive sequence integers, schema 1, mock channel, real UTC calendar timestamps and synthetic enum vocabulary. Add ingress-only limits: source event/lead/contact references `[A-Za-z0-9_.:-]{1,128}`, text at most 4,096 UTF-16 code units; occurred_at at most 24 characters. Shared location normalization/120-character trimmed limit and null-versus-omitted semantics remain unchanged. Total UTF-8 byte limit applies independently. Text may be empty; no free-text interpretation.
6. Hash exact raw bytes using pinned portable SHA-256. Invoke mandatory injected verifier with provider, method, path, headers, copied raw bytes and digest. There is no default verifier, no always-accept production implementation and no header-based tenant lookup.
7. Capture immutable verified principal metadata. Require provider/method/path/body digest to match the actual request. Principal/source/nonce must be bounded opaque reference strings; signed_at must be valid UTC, at most 24 characters, less than 300 seconds past or at most 30 seconds future of the injected server clock. The past cutoff is now exclusive so expiry at the exact deadline rejects consistently. These are test policy constants, not selected-provider limits. occurred_at is informational fact time; it is not freshness/ordering authority. Freshness binds the **authenticated signed_at**, never an unverified body/header timestamp.
8. Retrieve server-side source mappings by verified authority. Require exactly one result, not a default or first match. Its principal, provider and source must exactly match the verifier's authority. Require development environment and action `ingest_mock_lead`; authentication alone is not action authorization. Capture the mapping ID and exact version before further awaits. Require its status ACTIVE, valid positive safe-integer version and exact verified principal/provider/source/environment/action. Missing/ambiguous/wrong-source/wrong-action/inactive/revoked mappings fail closed. Resolution, durable nonce claim and replay-aware acceptance must identify the same original primary D1 binding; different binding objects fail closed, even if wrappers claim the same underlying database. Active tenant is checked before nonce binding; acceptance checks tenant activity and the complete captured source authority inside coherent reads and atomic writes, including replay.
9. Atomically claim scoped nonce identity against the complete current authority and active tenant. Distinguish first, identical, conflict and expired; conflict/expiry rejects before core. Then call the shared Processor with trusted mapping-derived context, validated data, captured source authority and the immutable bounded replay admission. The processor forwards that unchanged authority on every bounded retry; it never refreshes a stale mapping into a new grant. Core retains semantic fingerprint, event idempotency, sequencing, qualification and atomic D1/outbox invariants. No untrusted tenant reaches it.
10. Return 200 only after durable acceptance or immutable replay. Reply contains generated request_id and original internal event_id, not payload/qualification/tenant/provider identifiers. No external effects occur.

## Verification abstraction and future protocols

`Dependencies.verifier.verify` returns null or a `Principal`: principal, provider, source, signed_at, nonce, body_digest, method, path. This is a **trusted adapter output**, not a structure callers may supply as authorization. Adapter implementations must establish all those claims cryptographically or through an explicitly approved equivalent protocol. An OAuth token alone does not bind request bytes/source/time/nonce; a shared-secret header alone does not satisfy this contract. Future signatures, shared secrets and OAuth need reviewed authority, request-binding and replay mechanisms behind this interface. The raw body copy prevents adapter mutation of the bytes used for validation/hash.

Only test harnesses implement synthetic verification. Source mappings now have a real local D1 persistence adapter; synthetic tenant/mapping setup remains test-only, without an administration endpoint. They deliberately fabricate trusted metadata for control-flow tests; this is not proof of authenticity against any real protocol. Production adapter registration/credential scopes, provider canonicalization, key rotation, constant-time secret handling, OAuth audience/expiry/scopes, signature/timestamp coverage and source ownership remain blockers for real ingress.

## Persisted source authority and acceptance cutoff

`src/source-mappings.ts` defines the provider-independent `SourceMappingStore`/`SourceAuthority` contract and local `D1SourceMappingStore`. Each mapping stores generated UUIDv4 ID, monotonically increasing integer version, provider/source, authenticated principal, tenant FK, source binding, authorized operation/environment, ACTIVE/INACTIVE/REVOKED status, created/updated timestamps and terminal revoked timestamp/version. `(provider, source)` is globally unique: a routed source cannot ambiguously belong to two tenants or principals. No tenant/default is inferred from input. The store returns defensive frozen row copies, not live configuration objects.

The additive definitions live in the existing packaged `src/schema.sql`: source mappings and their version/tombstone triggers, durable replay rows and expiry index/ownership/immutability/tombstone triggers, and batch-local authority/replay assertion tables. Reapplying this schema installs the new objects without altering existing tables or dropping data. Tests apply it only to local bindings. There is no automatic remote migration, resource creation or rollout approval.

Local trusted setup uses `store.create(mappingFields)`, `store.update(scope,id,expectedVersion,{principal?,source_binding?,status?})`, and `store.revoke(scope,id,expectedVersion)`. These are maintenance primitives, **not an administrator authorization API**. Values are parameter-bound; create/update keys have fixed allowlists. Update/revoke compare tenant, ID and expected version in one `UPDATE ... RETURNING` statement. A foreign tenant, stale version or terminal revoked row yields sanitized typed denial. Updates advance version exactly once; inactive-to-active regrant explicitly advances version. The API cannot change tenant/provider/source/ID/creation identity. Direct trusted SQL movement of tenant ownership must also advance version and is rejected by an in-flight old authority; it is not an exposed transfer operation.

Physical deletion is prohibited by a persistent trigger, and REVOKED is terminal. A BEFORE INSERT collision trigger also rejects INSERT OR REPLACE/route or ID replacement, independent of SQLite recursive-trigger settings; REPLACE cannot silently delete a tombstone and restore an old active version. Routing tombstones permanently reserve provider/source; creation cannot recycle an old mapping ID/version or recreate that route. An update trigger rejects unchanged/reset/skipped versions, immutable routing/ID/creation changes, unsafe integer overflow and any mutation of a revoked row. Revocation does not erase accepted business records or retract already committed outbox intents. A future transfer/purge/regrant policy for terminal revocation needs separately reviewed design rather than bypassing these triggers.

`Ingress` requires matching persistence identities, and `Processor.process(...,authority)` passes the exact frozen authority to `AcceptanceRepository.accept(...,target,authority)` on every attempt. D1 checks **all** captured ID/version/provider/source/principal/tenant/source-binding/operation/environment fields and ACTIVE status, not version alone. Tenant/activity and source authority reads are in the same transactional batch as the exact event/lead/qualification snapshot. Duplicate replay linearizes at that coherent read batch: revocation committed before the snapshot denies even a previously accepted event; a replay read completed before revocation may return its original immutable outcome. There is no cached-success authorization shortcut.

New/update acceptance linearizes at the **actual atomic D1 write batch**. A named SQL CHECK requires the same full authority tuple to exist ACTIVE before any business writes. Zero authorization aborts the entire batch; JavaScript does not attempt to roll back after success. A change or revocation that commits before this batch produces zero new business/outbox effects, even if resolution, verification or planning already succeeded. Independent requests and mapping mutation serialize through the same primary database: acceptance completed first may succeed; revocation completed first must deny. A second asynchronous lookup before calling Processor would not satisfy this contract and is not the authority cutoff. Existing lead/event CAS, identity conflicts, bounded transient classification and ambiguous-commit reconciliation are unchanged. Source denial is a nonretryable context failure; a transport retry retains the original authority rather than silently granting a changed version.

No-authority SQLite/core and existing trusted D1 maintenance paths retain their original behavior. They are not authenticated ingress paths. The processor rejects supplied authority if the repository lacks authority capability; ingress rejects a missing/mismatched capability. Trusted custom adapters must enforce the same atomic persistence contract, not substitute an out-of-transaction memory callback. Binding identity is a compatibility check, not proof that arbitrary trusted adapter code is honest or that a wrapper secretly hiding a session is primary.

## Immutable composition, mutable authorization data

`Ingress` captures collaborator objects and bound verifier/resolve/claim/persistence-identity/repository methods once at construction into frozen narrow facades held in a runtime `#private` field. Replacing the caller's dependency object, collaborator objects, method properties, clock or logger during any await cannot rewire that instance. The D1 repository and mapping store capture their original binding methods, generator/clock identities and policy in runtime `#private` fields; repository helper methods are private too. No caller-owned global D1 object is frozen, so the emulator and platform receiver semantics remain intact.

This freezes wiring, **not source authorization data**. Legitimate persisted mapping changes remain visible and must invalidate captured stale authority. Injected adapters/functions remain trusted code: their bound receivers or closures must internally capture immutable configuration and must not request-mutate their own database, credentials or policy. A narrow facade cannot make malicious closures honest or deep-clone native platform capabilities. Construct a new ingress instance to deliberately change trusted adapter configuration; only synthetic tests use such recomposition. Runtime tests separately cover original-object/method replacement during verifier, mapping and replay awaits, repository configuration-field assignments, immutable proof/mapping capture and live persisted revocation.

## Replay and recovery contract

`src/replay-ledger.ts` defines provider-independent `ReplayClaim`, `ReplayAdmission`, `ReplayLedger`, outcome and typed failure contracts, plus the local `D1ReplayLedger` adapter. The ingress facade exposes only `claim` and its opaque `authorityBinding`; it does not expose maintenance. No memory nonce store remains in the ingress/authority harnesses. The ledger, source store and replay-aware repository must all report the same original primary binding object. Sessions are rejected. The repository advertises optional `replayBinding` capability; ingress requires it, while original no-authority SQLite/core and trusted D1 paths remain unchanged.

A verified claim contains the exact captured `SourceAuthority`, raw nonce, SHA-256 request fingerprint and authenticated signed timestamp. Nonce identity is SHA-256 of the unambiguous JSON tuple `(development, provider, principal, source, nonce)`. **Tenant, mapping ID and mapping version are deliberately excluded from the uniqueness key**: tenant movement or a new grant cannot reset a previously reserved nonce. The row binds the original tenant FK and mapping ID FK, a hash of every authority field (ID/version/provider/source/principal/tenant/source binding/environment/operation), request fingerprint and signed timestamp. Fingerprint covers method, path, signed_at, exact raw-body hash and resolved mapping ID/version/tenant/source binding. Signed timestamp is also compared independently by the ledger; identical caller fingerprints cannot conceal a changed timestamp.

Rows contain compact reservation metadata only: three 64-character hashes, tenant/mapping UUID references, integer signed/expiry/deadline times and one terminal-expiry flag. They contain no raw nonce, principal, provider/source token, request body, headers, credential or cached business outcome. SHA-256 references are pseudonymous, **not encryption or a claim of anonymity**; low-entropy references can be guessed. They are not logged. Production classification, access and retention decisions remain required.

Claim is one atomic primary D1 batch: assert exact current mapping authority plus active tenant; clear the assertion; insert only if the scoped nonce does not exist and SQL freshness passes; retrieve at most one row filtered by nonce reference **and captured tenant**; retrieve database clock metadata. All values are parameter-bound and identifiers/SQL are fixed. The insert uses database uniqueness/serialization, not a global JavaScript queue or process-local lock. A no-row result for an existing foreign reservation is a neutral conflict with no admission or foreign identifiers/counts. First/identical results carry only an admission descriptor; conflict/expired results carry only the closed outcome. Claim never grants authorization, consumes an irreversible one-shot success flag or caches an accepted response.

### Synthetic clock and lifetime policy

- Past authentication window: 300,000 ms, exclusive at expiry. Future skew: at most 30,000 ms. Event occurred_at remains informational. Ledger SQL independently enforces future skew using the database clock.
- Authentication expiry is immutable `signed_at + 300,000 ms`; there is no sliding retry window. Future skew is an admission allowance, not another 30 seconds added to an old signature's expiry.
- One nonce also has a conservative maximum in-flight/recovery admission of **30,000 ms from first claim**, capped by authentication expiry. SQL caps the stored deadline against database time; an application clock ahead cannot extend this lifetime. A conservative earlier application deadline/clock may deny sooner. Identical retries return the original deadline and never renew it. Recovery outside this shorter admission requires fresh authentication with a **new nonce**, even if the old signature's five-minute window has not ended.
- SQLite/D1 `julianday('now')` converted to integer epoch milliseconds is the atomic database clock. Acceptance compares the deadline with `max(validated application-clock observation, database now)`: capture a new observation for the coherent read snapshot (including duplicate replay), and again when building each pre/post-write SQL guard after planning. Private repository clock validation preserves captured wiring and rejects invalid UTC timestamps before business writes. Database now evaluates inside each actual batch statement; JavaScript cannot observe an application-clock change during SQL execution. The final SQL assertion therefore uses its latest pre-batch application observation plus the database clock, not a fictional JavaScript callback inside D1. Claim and acceptance retries refresh observations without renewing the immutable original admission. Tests use actual local clock timestamps for signed requests, not the historical fixture's fact timestamp. Clock correctness/rollback and remote D1 time semantics must be qualified before live operation.
- Claim expiry is enforced inside the actual atomic SQL insert, not just before an awaited batch. A transport delay that crosses expiry inserts no reservation. The coherent acceptance read batch checks the owned reservation, exact authority/fingerprint/deadline and non-expired status; an immutable duplicate linearizes at that read snapshot. New/update acceptance checks freshness both **before and after all business writes in the same atomic batch**. A failing final SQL CHECK rolls back every business/outbox write. No check-before-await permits a delayed stale acceptance. Commit's internal finalization is the database boundary, not a claim of continuous authorization after a transaction completes or bounded network response latency.

`Processor` captures and forwards the same replay admission on every attempt; it neither reclaims nor refreshes authority/deadlines. Source authority and tenant guards remain authoritative in addition to replay guards. Mapping revocation or a changed tuple before claim denies without a nonce row; changes after claim but before acceptance still deny at the existing actual acceptance boundary. A durable identical claim cannot bypass current mapping/tenant authorization or the core's event identity, sequence and CAS guards.

### Expiry, retention and recovery

Trusted `ReplayMaintenance.expire(scope,limit)` marks at most 1–100 expired owned rows in one parameterized statement, using the tenant/expired/deadline index and active tenant predicate. It is a trusted maintenance primitive, **not an administrative authorization API**, and is not exposed through ingress. Foreign tenant cleanup cannot mutate the original reservation. It changes only `expired: 0 → 1`; immutable metadata stays compact and unchanged. There is no physical purge, payload retention or automatic scheduled cleanup in this slice.

A terminal tombstone **permanently reserves the scoped hash**. Expired retries are rejected whether or not cleanup ran. Deletion, mutation/renewal and INSERT OR REPLACE resurrection are prohibited by persistent triggers independent of recursive-trigger settings. Insert ownership checks current mapping/tenant association; FKs preserve historical tenant and mapping references after a separately trusted, versioned mapping movement. The original ownership is not rewritten. Same routed nonce under a new tenant/version remains conflict/expired, never a fresh reservation. This deliberately grows one compact row per admitted nonce without a retention horizon: acceptable for this synthetic local slice, **not an approved production storage/PII-retention policy or abuse quota**. Any physical purge/reuse, source transfer or compaction scheme needs separate reviewed approval; none is implemented by silently dropping conflict information.

Claim and business acceptance are separate commits on the same database, not one cross-system transaction. A durable claim without a business event is recoverable by identical retry inside its deadline. Claim alone creates no event/outbox. Known D1 transient errors use the existing exact allowlist and completeness-bounded, cycle-safe cause classifier; unknown/permanent/contradictory/deep/cyclic details do not get blind retries. Claim owns a separate bounded whole-claim budget of 0–3 retries, default three (**four total attempts**), followed by safe unavailable. Acceptance retains its existing independent whole-business-unit budget and unchanged atomic guards. These budgets are sequential finite boundaries, not a nested/unbounded reconciliation loop. A lost claim response can recover as identical on the next permitted attempt. Final-attempt exhaustion does **not** prove rollback; explicit replay can find the committed reservation. No extra hidden read or unlimited retry conceals exhaustion. Maintenance errors use sanitized typed denial/unavailable/failure without an automatic retry loop.

Core durable identity is `(tenant, source_binding, source_event_id)` with its existing canonical semantic fingerprint. Same event/same semantic input under a fresh valid authentication can return the original internal event/outcome; same event/changed semantic input conflicts even with a new nonce. Exact same-nonce retry is stricter: byte-different JSON conflicts, even when semantic input is equal, and is allowed only inside the original bounded admission deadline. After freshness expires, recovery requires newly authenticated delivery with a new nonce and current timestamp; the original semantic event identity remains unchanged. A 503/500 does not prove rollback. Explicit replay reconciles an already committed outcome without duplicate action intent. This test executes real local D1 acceptance and then injects response loss on each allowed application attempt, followed by successful explicit replay.

## Safe errors and closed logging

| Status | Safe code / meaning |
| --- | --- |
| 400 | invalid_input: malformed JSON/UTF-8/schema/stream |
| 401 | unauthenticated: missing/rejected or mismatched verified proof, stale/future authentication, expired claim or acceptance admission |
| 403 | forbidden: missing/ambiguous/inactive/revoked/changed/unauthorized mapping, inactive context |
| 404 / 405 / 415 / 413 | route / method / media_type / too_large |
| 409 | conflict: nonce reuse or core event/sequence conflict |
| 503 | unavailable: existing bounded persistence retry budget exhausted, possibly committed; also known transient mapping-store failure or exhausted durable claim retries |
| 500 | internal: unexpected/permanent/unknown persistence, resolver/verifier/ledger errors |

Only typed known boundary/core errors are classified; raw database messages, exceptions, causes, headers, payloads, stacks, secrets and PII are never returned or logged. Permanent/unknown failures are not blindly retried by ingress; the ledger owns bounded claim retries and existing Processor owns bounded acceptance retries. Response headers set no-store and nosniff. All responses carry generated request_id. The log callback receives only `{request_id,status,code,provider_category,replay_outcome,failure_category}` with closed TypeScript field unions. Provider category is the fixed allowlist `synthetic`, `other`, `unknown`, never the supplied route/provider token. Replay outcome is the claim result (`first`, `identical`, `conflict`, `expired`) or `not_claimed`; failure category is a safe response code or `none`. The generated request UUID is the safe trace reference, not a raw/body/nonce hash. No fingerprint is logged; no spread of input/exception objects, external IDs or tenant labels. Logger exceptions are swallowed to avoid changing an already committed result; production monitoring of logger health is a future operational requirement.

### Implemented deadline and cancellation boundary

`Ingress` accepts optional trusted `OperationalOptions`; the default synthetic request budget is **10,000 ms**, with configurable integer budgets **1–30,000 ms**. One `Deadline` is created once per handle call, not renewed for stages/retries. It owns a Workers-compatible timer, an AbortController, captured observation clock, and a closed `DeadlineError`. Request AbortSignal interruption uses the same fail-closed cancellation path. The operational observation clock is distinct from the original authenticated/replay UTC clock; changing the request budget never changes stored replay deadlines or signature expiry.

The bounded pipeline races against that single deadline. Checks bracket body reads, raw validation/hash before verification, verifier completion, source resolution, active scope, authenticated quota, durable claim, acceptance planning/retry entry and response acknowledgement. Verification receives an optional AbortSignal; the durable local claim adapter accepts an optional operation guard and checks before every attempt and after success/failure, so a late transient failure cannot launch another claim attempt. Acceptance uses a per-request guarded repository facade: it checks at each shared Processor attempt and inside the planning callback after the coherent D1 snapshot and before its return. The actual shared Processor, retry classification/budgets and atomic D1 acceptance implementation are unchanged. After cancellation, late verifier/mapping/claim/snapshot completion cannot start a new downstream stage or acceptance retry. Failed/invalid operational clocks produce safe internal/deadline rejection with no new claim. Trusted collaborators must keep synchronous work bounded; an arbitrary synchronous logger/verifier or parser cannot be forcibly preempted by JavaScript.

Body reading retains the strict **16,384-byte** limit, fatal UTF-8, strict schema and decoded duplicate-key inspection. A separate **16,384-chunk read budget** includes empty chunks, preventing an empty-chunk stream from retaining an unbounded array or monopolizing reads independently of its byte count. Bytes are copied into bounded chunk buffers. Overflow cancels the reader; slow/interrupted streams are canceled by the deadline. Cancellation is invoked once, its rejection is consumed, and its actual completion belongs to the tracked body work. A hung underlying cancel promise therefore does not free a permit merely because a timeout response was returned. With a responsive cancel, overflow is still 413; if cancellation itself hangs, the common deadline can return 504 instead. No untrusted Content-Length bypass exists.

**Cancellation is not D1 rollback.** D1's documented batch API has no AbortSignal/transaction-cancellation parameter. Once a batch is issued, a timeout cannot retract it: a delayed guarded batch may commit after the HTTP/RPC response became 504. Existing full tenant/source authority and immutable nonce/freshness assertions remain inside the actual atomic batch, including its final replay assertion. A revocation committed before that delayed batch still aborts all business/outbox effects; a still-authorized batch inside the original durable deadline can legitimately commit late. Already committed D1/outbox rows are never described as rolled back. Explicit newly authenticated, idempotent recovery reconciles either a claim-only reservation or a committed event, inside the **original** nonce admission; identical replay never renews its 30-second/authentication-capped deadline. Outside that deadline, use current authentication and a new nonce while preserving semantic event identity. A 504, 503 or transport loss is ambiguous, not permission for blind retry or duplicate action intent. No post-timeout recovery loop is started by ingress.

### Implemented local admission and rate policy

Admission is synchronous **zero queue**. Module-default counters are shared across locally constructed ingress instances in one isolate: at most **16 actual in-flight pipelines**, at most **16 per verified source identity**, and at most **128 tracked source keys**. Trusted custom construction may use smaller `LocalAdmission` limits; constructor bounds are 1–1,024. Source keys hash the unambiguous verified `(provider, principal, source)` tuple; neither tenant claims nor caller headers select them. Source admission follows exact active mapping validation; global admission precedes body/authentication to bound unauthenticated expensive work. There is no request/tenant/body/I/O object in the counter maps. Global/source method identities, rate-policy methods and options are captured at composition, so replacing caller-held methods during an await cannot rewire this instance.

Permits release in **actual pipeline settlement**, not response-race settlement. A timed-out verifier, body cancellation, claim or issued D1 batch that remains pending still occupies its permit. Permanently hung trusted work can exhaust capacity and deny further arrivals: this deliberately trades availability for a truthful work bound. Nothing is queued, no late continuation obtains a fresh permit, and settled source entries are deleted. Explicitly constructed ingress instances with private limits are private budgets; share one injected `LocalAdmission` when they must belong to the same local budget. These counters are process/isolate-local scheduling protection, **not distributed tenant isolation, authentication, exact accounting or a global Cloudflare abuse quota**.

`RatePolicy` is a synchronous injected **local/mock adapter only**, with separate `preauth()` and `authenticated({provider,principal,source})` decisions. It cannot receive an unverified source/tenant/header or caller-selected privileged tier. Pre-auth traffic uses one anonymous global bucket and can consume that shared protective bucket, but cannot burn a victim's authenticated source bucket by claiming its header identity. Authenticated quota runs only after verified proof, exact active mapping and active tenant checks, before nonce/business writes. Authentication/authority uncertainty fails closed before that quota. Its counters do not replace atomic acceptance authorization; live revocation remains enforced by D1.

The default `LocalRatePolicy` is a fixed-window synthetic policy: **1,000 pre-auth arrivals / 10 seconds**, **100 authenticated arrivals per verified source tuple / 10 seconds**, at most **128 hashed source buckets**. Windows are captured finite 1–60 second intervals; source maps clear only on whole-window rollover, not per-key eviction. Cardinality saturation denies new buckets for the remainder of the window instead of evicting a used bucket to allow quota bypass. Counter increments/decisions are synchronous. Invalid clocks fail closed and rollback cannot renew a window. Denial returns a bounded **integer Retry-After 1–60 seconds**, calculated as the rounded-up remaining local window; it is a retry hint, never a reservation or guarantee of later success. Invalid/malformed adapter decisions or retry intervals return safe 500, not untrusted headers. Trusted injection may mock different decisions; it is not an exposed policy-selection API. No Cloudflare Rate Limiting binding, WAF rule, Durable Object, configuration or remote service call is built.

Future production strategy requires separately approved edge pre-auth protection, correctly verified source keys and reviewed distributed coordination. Cloudflare's documented Rate Limiting binding is **location-local, permissive and eventually consistent**, not accurate accounting or a global concurrency/security boundary. Its documented simple periods are 10/60 seconds; neither that API nor a client-controlled `userId` example establishes our authority. If exact distributed admission/accounting is required, choose and review a coordinated strategy separately; local counters must not be advertised as satisfying it. Production source aliases/principal rotation, fairness, quota policy/retention and permanent tombstone storage growth remain design gates.
